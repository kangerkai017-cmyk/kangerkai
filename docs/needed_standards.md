# 后续需要收集的主线规范清单

> 状态：资料补全清单。用于指导后续人工收集、清洗和交给 chunk pipeline 的规范资料。
> 本清单只保留与当前事故案例和论文主线直接相关的规范；不再列条件触发或边缘设备管理规范。
>
> 当前原则：
> - 规范管道已固化为通用版本（`norm_chunker_v2` + cjk 检索 + tags.yaml 词表）。新增规范无需改代码：把可抽取文本的 PDF/DOCX 放入 `rag_data/` 或 `脚手架规范文表图切分/` 源目录，重跑 `scripts/build_norm_chunks.py` + `scripts/build_norm_index.py` 即可。
> - 新领域/新术语只需在 `data/taxonomy/tags.yaml` 扩充关键词或 `standard_tag_hints`，这是唯一人工维护点。
> - 新增规范资料先人工处理为可抽取文本，再按 `docs/chunking_guide.md` 生成 norm chunks。
> - 新增规范 chunk 通过校验后，重建 `safety_norm_chunks`。
> - 事故案例资料补齐后，生成 case chunks 并构建 `safety_case_chunks`（case 管道尚未实现，见 `next_phase_data_chunk_plan.md`）。
> - mock 数据不得进入正式索引。

## 目标格式

新增规范资料建议提供以下任一形式：

- 可复制文本的 PDF，优先。
- 已按章节、条文、表格、图像说明整理好的 Markdown。
- DOCX 原文或清洗后的 TXT/Markdown。
- 对扫描版 PDF，先做 OCR，再人工抽查条文号、表格、图像说明是否完整。

每份资料至少保留：

- 规范名称；
- 标准编号；
- 年份；
- 原始文件路径；
- 章节标题；
- 条文号；
- 表格或图像说明；
- 页码或可追溯位置。

## 事故案例来源材料

事故案例后续进入 `safety_case_chunks`，不直接替代规范要求。

每个案例最好保留：

- 原始 PDF；
- 原始 HTML；
- 网页截图；
- 或整理版 Markdown。

每个案例至少补齐：

- 事故标题；
- 事故类型；
- 发生日期；
- 来源单位；
- 来源路径；
- 事故经过；
- 原因分析；
- 后果；
- 整改措施。

## 后续交付给 Chunk Pipeline 的要求

新增规范或案例资料交给 pipeline 前，应确认：

- 文件可以稳定读取；
- 条文号、表格编号和图像说明没有明显错乱；
- 来源路径可追溯；
- 不混入 mock 示例；
- 新增标签先进入统一词表；
- 生成 JSONL 后必须产出导入报告；
- 导入报告中 duplicate `chunk_id` 数量为 0；
- 正式索引构建后，ES count 等于 JSONL 行数。
